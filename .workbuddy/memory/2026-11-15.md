## 修复 Lottie 高光缺失与预览白闪（11:55）

用户「是不是缺失了一个左上角的高光，另外怎么屏幕会闪白一下」。

- 根因（高光）：`icon.svg` 注释写明高光是 "in the tile colour, so it reads as a cut-out"，
  即原品牌图标靠**白色地砖**透出来形成高光。深色/透明动画没有白地砖，之前照搬
  「挖空」语义：GIF/WebP 用 `soft_mask(bell, sheen)`，Lottie 用 `masksProperties.mode="s"`
  subtract mask，结果左上角变成暗洞/纯蓝平涂，白色高光消失。
- 修法：GIF/WebP 改 `soft_mask(bell)`，在 bloom 之后叠加真实白色高光（core 0.96 +
  淡青 aura 0.24，均裁剪在伞盖内）；Lottie 删掉 subtract mask，新增最上层
  "Specular highlight" 图层（白色 fill 96% + 淡青 halo stroke），路径仍由
  `highlight_shape` 关键帧驱动，随呼吸伸缩。图层由 3 变 4，首尾形状仍逐点相同。
- 根因（白闪）：预览页 `<html>` 背景透明、无 `color-scheme` meta，宿主 webview 在
  CSS 首帧前先画默认白底；且 lottie-web 的 subtract mask 会在 `<defs>` 里放一个
  480×480 `#ffffff` 矩形，循环缝上也有白闪观感。
- 修法：head 最早处加 `<meta name="color-scheme" content="dark">` + `theme-color`，
  `<html>`/`<body>` 内联 `#0b1220`，CSS 补 `html,body{background:#0b1220}`；
  `#lottie` 初始 `opacity:0`，`DOMLoaded` 后加 `.ready` 才淡入；棋盘底 `#fff` 改
  `#eef3f9`。去掉 mask 后 SVG 里已无白色矩形。
- 验证：真实浏览器 DOM 检查 masks=0 / 白色矩形=0 / html+body 背景 rgb(11,18,32) /
  白色高光 path=rgb(248,252,255) / ready=true；深色、浅色、棋盘三底截图高光均可见，

## 确认 animated WebP 透明背景（12:36）

用户「webp背景能透明吗」。答：能，且 `jellyfish-breathe-alpha.webp` 本来就是透明底。

- 结构实证（直接解析 RIFF chunk，非仅看 Pillow 属性）：`VP8X` flags 0x12 =
  alpha + animation，画布 480×480；`ANIM` bgcolor BGRA `#00000000`（透明黑）、
  loop=0；36 个 `ANMF` **全部**带 `ALPH,VP8` 子块，首帧 `dur=80ms`、
  `blend=no-blend`、`dispose=to-bg`。逐帧 alpha 直方图：全透明约 8.0-8.8 万、
  全不透明约 6.7-7.1 万、半透明约 7.6-7.9 万像素。
- 结论：若某看图软件显示白/黑底，是该软件不合成 alpha 而用画布底色填充，
  与文件无关；换浏览器即可。GIF89a 只有 1-bit 透明索引，做不到这些半透明
  发光与抗锯齿柔边，这正是另做 WebP 的理由。
- 新增产物（仍在系统临时目录、未进仓库）：`jellyfish-breathe-alpha-poster.png`

  （自包含 1.77 MiB，data URI 内联 WebP 三栏深色/纯白/棋盘底对照）。

## WebP vs Lottie 资源开销基准与动画资源归位（12:46）

用户「webp版本是不是比lotttie更节省资源」「如果页面有很多个呢」
「提交，把public/logo也提交 提交两种动画」。

- 静态体积：WebP raw 1,327,332 B / gzip 1,326,876 B（已压缩不再缩）；
  Lottie JSON 451,166 B → gzip 55,359 B，lottie-web 5.12.2 min 305,543 B →
  gzip 76,062 B。完整 Lottie 传输 128 KiB，比 WebP 省约 10 倍；raw 合计
  0.72 MiB vs 1.30 MiB。结论：体积/传输 Lottie 胜，缩放、改色、暂停调速也胜。
- 运行时（headless Chrome + CDP Performance，3 秒稳态、单实例）：WebP
  ScriptDuration≈0、TaskDuration 2 ms、JS 堆 2.4 MB、节点 30；Lottie svg
  renderer 356 ms / 612 ms / 23.1 MB / 85 节点。原因是 WebP 走原生解码器逐帧
  blit、零 JS；Lottie 每帧做 4 层 × 19 关键帧 × 137 顶点插值并写 SVG `d` 属性，
  还触发布局与样式重算。
- 多实例 N=1/4/8/16：WebP JS 恒定 15/12/13/12 ms、Task 84/91/81/81 ms、
  堆 1.4/26.8/57.1/75.9 MB；Lottie JS 366/798/1255/2097 ms、Task
  625/1106/1672/2825 ms、堆 26.0/56.5/98.9/205.9 MB、节点到 961。N=16 时
  Lottie 占 70% 主线程 JS、94% 主线程任务。同一资源的多个 `<img>` 共享解码
  帧缓存；每个 `loadAnimation` 是独立动画对象 + 独立 SVG DOM + 独立 rAF 回调，
  故 CPU/内存近线性叠加。Tauri 多窗口各自独立 webview，堆不共享，差距更大。
- caveat：headless 的 rAF 由虚拟时钟驱动（各档约 430 帧/3 秒），不能据此判定
  真机掉帧；测的是 svg renderer，换 canvas 会好一些但不改变量级。
- 选型：同页/跨页多实例一律 WebP 或静态透明封面；单个主角且必须矢量/改色才用
  Lottie。要用多个 Lottie 的收益排序：IntersectionObserver 暂停离屏实例 →
  单实例 canvas 渲染后 drawImage 复制 → 静态封面 + 仅激活时播放 →
  canvas renderer → 降帧率/简化路径。
- 资源归位：`public/logo/animation/` 放 `jellyfish-breathe-alpha.webp`、
  `jellyfish-breathe.json`、`jellyfish-breathe-alpha-poster.png`、
  `jellyfish-breathe-lottie.html`（自包含离线预览）；`scripts/` 放两个生成脚本
  与 vendored `lottie-web-5.12.2.min.js`。脚本路径全部改为基于 `__file__` 的
  相对路径：交付物写仓库、GIF/sheet/arms 写系统临时目录；实测两次生成逐字节
  一致、无 pycache。原先的 alpha-poster 是从有损 WebP 解码出来的，现改为脚本
  直接保存无损原始帧。
- `public/logo/v1/` 是另一套「水母 LOGO 高清矢量重绘」（300 viewBox，
  512/1024/2048/4096 PNG + 自己的 hd-preview.html），与呼吸动画源自
  `src-tauri/icons/icon.svg` 不同源，两套不要混用。项目仍无 lottie-web 依赖，
  预览页内联的库仅供离线预览，应用内要用 Lottie 需另装依赖。
